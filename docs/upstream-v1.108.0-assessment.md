# LiteLLM v1.108.0 同步评估

评估日期：2026-11-04

可以迁移到 v1.108.0，但需要整合定制代码、重新构建和隔离验收，不能直接更换线上镜像标签。本次仅执行仓库比较和不修改工作区的 Git 试合并，没有升级线上服务，也没有执行新版应用测试

补充评估后，日常维护更适合采用同维护线补丁加按需回移修复，整体迁移作为需要新版能力时的选项。前次的 198 个冲突是整体迁移模拟的结果，不是每次补修复必须支付的成本

## 需要人工整合的部分

计费核心 `litellm/cost_calculator.py` 存在价格优先级判断冲突：定制使用 `custom_pricing is not True`，新版使用 `not custom_pricing`。需要结合允许值和分组倍率回归测试判断，确保自定义价格、上游返回费用、预扣与实际结算的关系一致

权限类型 `litellm/proxy/_types.py` 中，只读管理员路由白名单的定制用户查询入口与新版遥测入口冲突，需要保留各自适用的权限边界。用户编辑页的翻译属性与新版 `userId` 属性冲突，需要同时保留中文化和新版用户范围限制

三个 `schema.prisma` 都存在冲突，需要合并 commerce 模型与新增上游模型，保持三份结构一致。新版相对基线新增七个迁移文件，涉及失败请求统计、用户供应商凭据、遥测和访问组 MCP 工具及 Skills 权限。应在隔离数据库先按现有迁移历史应用，不修改已部署迁移，不在启动迁移中重写业务数据

前端还需要处理用户组、模型、Playground、导航、首页和生成的 OpenAPI 类型。保留现有 Logo、中英文切换、客户菜单和原有界面风格。`src/lib/http/schema.d.ts` 应从合并后后端重新生成，不手工选择旧版或新版文件

后端依赖与 `uv.lock` 必须一起整合。目标版本更新 proxy extras 和 enterprise 包版本，并放宽 Python OpenAI SDK 上限。前端增加 Lens 归档包并调整依赖，不能只复制组件而沿用旧锁文件

鉴权、日志、预扣和调用结算相关文件即使自动合并也需要回归测试。没有文本冲突只说明 Git 能组合文件，不能证明余额检查、分组禁用、Key 权限和流式扣费行为正确

## 已有保护与暂缓变更

当前计费核心已用 `custom_pricing is not True` 保护定制价格，覆盖了 [#46120](https://github.com/BerriAI/litellm/commit/f97d3df6de8bb04ab8bb59117f41e515c4364449) 处理的“上游费用覆盖定制价格”问题方向，应测试等价性而非机械重复回移。当前 LoggingWorker 已将切换事件循环时的待处理任务迁移至新队列，发布说明中的同类修复不能直接算作缺失

当前基线历史已包含证书根更新 #47670、断开流的费用记录 #47611、完成请求不再误记 499 #47652、Postgres 重启后重排费用日志 #47571 等回移提交。它们需要作为余额和日志回归范围保留，不应仅因在新版修复清单出现就再次应用

线上数据库在本轮只读查询中列出 `deepseek-v4.1-flash`、`deepseek-v4.1-flash-1017`、`deepseek-v4.1-flash-uncensored`、`gpt-6-luna` 和 `gpt-6-luna-decisions`。这只是数据库模型目录快照，不代表所有运行时功能和配置的完整清单，也不能单凭公开模型名判断底层部署是否使用云平台

Lens 独立服务与 UI 包迁移、界面组件库重构、Rust 路由结构调整、Copilot 新供应商和新增遥测页，暂不作为本轮业务修复的交付目标。未使用的云供应商、视频、SAML、RDS IAM、读副本和 Redis Cluster 专属修复可暂缓，启用对应能力时重新核对。共享鉴权、HTTP、流式和日志依赖不能仅因标题提到未使用的供应商就跳过

Copilot 的每用户 GitHub OAuth 用于连接模型供应商凭据，与 CocaAPI 的 GitHub/Google/NodeLoc 注册登录不同。原生 `/v3/login/exchange` 的 Cookie 修复 #45840 也应按实际登录链路评估，不能代替或直接改写 `/account/api/v1/oauth/` 的自建登录流程

新增模型条目和价格更新单独审查，不自动改变现有售价、分组倍率或用户模型权限。测试、CI、文档和重构不因不直接提供业务功能就一律忽略，选中修复所依赖的测试及代码移动必须一起核对

祖先检查退出码 0；试合并退出码 1，仅 `uv.lock` 存在冲突，没有前端冲突。相比整体迁入 v1.108.0 的试合并，文本整合范围明显较小，但仍需核对依赖和 Lens 部署行为，不能据此宣布运行兼容。该维护版也不能代替前述精选修复的逐项核对

## 后续维护方式

优先评估同维护线发布，日常只回移有明确业务收益或安全必要性的修复，记录上游提交、依赖、当前是否等价和行为测试结果。能独立应用的提交可用 `cherry-pick -x` 保留来源，依赖新版重构的补丁按修复意图适配，不强行带入整批重构。按需回移只缩小变更面，仍需要版本依赖检查和部署验证

不需要每次从新版基线重新搬运所有定制。完整同步时应保留真实的上游合入关系，并记录合入点，后续比较该点到新版本的增量。此次 198 个冲突包含维护分支分叉和 Lens 拆分的集中影响，不代表以后每个版本都会出现相同数量的冲突；只做 cherry-pick 也不会自动把上游祖先关系推进到目标版本

仅回移修复后继续保留真实的上游运行时版本，并用 CocaAPI 构建版本或 revision 标识补丁集合，不能把版本号改成 v1.108.0 来声称完成升级。同维护线停止维护、补丁依赖链过长、出现必须使用的新能力或运行时升级要求时，再集中进行跨版本整合，避免长期冻结旧基线

现有整文件 COPY 核心模块和大量界面内嵌翻译会放大维护成本。后续在触及相关功能时逐步收敛到回调、共享权限服务和集中翻译入口，减少覆盖范围；这不是本轮修复回移的前置大重构，也不通过删掉中文化、权限或扣费检查来降低冲突

## 需要整体升级时的执行顺序

先以固定的 v1.108.0 提交建立隔离升级候选，迁入当前定制差异，并核对维护分支独有修复。优先整合数据库、鉴权、用户组权限、计费钩子及依赖，再处理中文化和前端组件迁移，最后重新生成 API 类型并构建静态界面

构建必须使用真实的 v1.108.0 运行时。`deploy/cocaapi/Dockerfile.auth` 和 `deploy/cocaapi/compose.yaml` 当前固定在 v1.106.6，应更新为核验过签名和 digest 的目标镜像。定制 Dockerfile 会覆盖整个上游核心模块，需逐项审查 COPY 清单，防止旧模块覆盖新版修复。当前用于增量发布的旧运行时镜像不能作为升级后的基础镜像

隔离验证应覆盖注册与身份验证、GitHub/Google/NodeLoc OAuth、只读管理员限制、用户详情与余额流水、用户组授权及倍率、Key 权限、余额不足阻断、并发预扣、流式与非流式结算、失败释放预扣、支付通知幂等、订单超时、兑换码重复限制和邀请奖励。按相关目录现有测试约定运行聚焦测试，执行前端类型检查、构建和静态导出，再通过浏览器与真实 API 请求验证实际行为

上线前备份数据库和配置，记录回滚镜像及数据库兼容范围，在隔离恢复的数据库上核对原有用户、钱包和流水。镜像回滚不能撤销数据库迁移，需要单独验证旧程序对新增结构的兼容性。完成这些检查后再安排生产切换，不自动更新模型价格或更换商户及 OAuth 凭据

本次结论仅为可迁移性评估。198 个冲突路径尚未解决，依赖安装、数据库迁移、应用测试、构建及生产验收均未在 v1.108.0 候选上执行
